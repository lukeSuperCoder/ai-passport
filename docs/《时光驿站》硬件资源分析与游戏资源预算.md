# 《时光驿站》硬件资源分析与游戏资源预算

> 文档状态：首版资源预算  
> 目标硬件：FoloToy AI Passport（ESP32-C3）  
> 目标内容：《时光驿站》第一版 MVP  
> 前提：不考虑 OTA，单一本地固件，无 PSRAM  
> 相关文档：[《时光驿站》第一版 MVP 功能设计](./《时光驿站》第一版MVP功能设计.md)

## 1. 结论摘要

FoloToy AI Passport 的 8 MB Flash 可以容纳《时光驿站》第一版 MVP 的全部玩法、剧情、美术和音频内容，但必须改用自定义分区，并对美术、字体和音频使用适合嵌入式设备的存储方式。

该平台的主要限制不是 Flash 总量，而是无 PSRAM 条件下的内部 RAM、DMA 内存和最大连续空闲块。资源应常驻 Flash 并按需分块读取，不应将整张全屏图片、整段 PCM 音频或大型解码结果长期保留在 RAM 中。

建议的总体红线为：

| 项目 | 目标 | 硬上限/警戒线 |
| --- | ---: | ---: |
| App 固件镜像 | ≤ 1.70 MB | 2.00 MB 分区 |
| 游戏资源实际使用 | ≤ 4.50 MB | 5.81 MB 分区 |
| 单页新增动态 RAM | ≤ 24 KB | 不建议超过 32 KB |
| 普通单次连续分配 | ≤ 16 KB | 特殊情况不超过 32 KB |
| 运行时最低空闲堆 | ≥ 32 KB | 必须实机验证 |
| 最大连续 DMA 空闲块 | ≥ 16 KB | 必须实机验证 |

## 2. 数据可信度说明

本文档将数据分为三类：

- **已确认**：来自芯片规格、板级配置或当前源码的确定数据。
- **设计估算**：用于指导开发的预算，不是已编译固件的实测值。
- **待验证**：需要 ESP-IDF 构建产物或实机日志才能确定。

当前工作区没有 `build/*.map`、固件 `.bin` 和实机堆内存日志，因此不能将“当前固件精确占用”和“启动后精确剩余 RAM”当作已知数据。

## 3. 当前硬件资源

### 3.1 MCU 与存储

| 资源 | 容量/状态 | 可信度 | 说明 |
| --- | ---: | --- | --- |
| MCU | ESP32-C3 | 已确认 | 单核 RISC-V，目标配置为 `esp32c3` |
| 内部 SRAM | 400 KB | 已确认 | 不等于全部可用堆；系统、静态数据、任务栈和 DMA 共享 |
| PSRAM | 无 | 已确认 | 不能依赖外部 RAM 存放帧缓冲、音频或解码结果 |
| Flash | 8 MB | 已确认 | `sdkconfig.defaults` 固定为 8 MB |
| 显示 | 240 × 320 RGB565 | 已确认 | ST7789P3，SPI2 40 MHz |
| 音频 | ES8311 + I2S0 | 已确认 | 当前 BSP 使用全双工 TX/RX |

400 KB SRAM 中有部分必须由芯片、ESP-IDF、FreeRTOS、链接器段、驱动和静态对象使用。因此，游戏不能按照“400 KB 减去几个已知 buffer”的方式直接计算可用堆。

### 3.2 当前已知 RAM 占用

| 项目 | 大小 | 生命周期 | 可信度 |
| --- | ---: | --- | --- |
| LVGL 内部内存池 | 24 KB | LVGL 初始化后常驻 | 已确认 |
| LCD DMA 单缓冲 | 9,600 B | 显示初始化后常驻 | 已确认 |
| I2S TX DMA | 约 5.6 KB + 描述符 | 音频通道初始化后常驻 | 设计估算 |
| I2S RX DMA | 约 5.6 KB + 描述符 | 音频通道初始化后常驻 | 设计估算 |
| Audio demo 任务栈 | 4 KB | 进入 Audio 页时 | 已确认 |
| 播音临时缓冲 | 1,024 B | 播放方波时 | 已确认 |
| 3 秒录音缓冲 | 96,000 B | 录音回放时瞬时分配 | 已确认 |

LCD buffer 计算：

```text
240 像素 × 20 行 × 2 B/RGB565 = 9,600 B
```

当前 96,000 B 录音缓冲是最大的单次连续堆分配，与游戏运行时资源预算冲突。正式游戏不需要录音时，应去掉该功能，并将音频链路改为只创建 TX 通道。

### 3.3 全屏缓冲成本

一张 240 × 320 RGB565 全屏图在 RAM 或 Flash 中的原始大小为：

```text
240 × 320 × 2 B = 153,600 B = 150 KiB
```

在无 PSRAM 的 ESP32-C3 上，不应分配全屏 RGB565 帧缓冲。图片解码、转色和绘制应按行或小块执行，并尽量复用现有 20 行 LCD DMA buffer。

## 4. 当前 Flash 使用限制

当前仓库没有自定义 `partitions.csv`，`sdkconfig.defaults` 也没有选择自定义分区。新构建通常会使用 ESP-IDF 默认 single-app 分区：

| 分区 | 默认大小 |
| --- | ---: |
| NVS | 24 KB |
| PHY init | 4 KB |
| Factory app | 1 MB |

在这种配置下，8 MB Flash 中从 `0x110000` 到 `0x800000` 的约 6.94 MiB 空间没有分区，游戏不能直接用它存放资源。同时，所有编译进应用的代码、字体和图片都需要与现有固件共享 1 MB app 分区。

因此，开发《时光驿站》前必须先建立自定义分区表。

## 5. 推荐的无 OTA Flash 分区

推荐使用单一 2 MB app、5.81 MB 只读资源区和 128 KB 存档区：

```csv
# Name,     Type, SubType, Offset,   Size
nvs,        data, nvs,     0x9000,   0x6000
phy_init,   data, phy,     0xF000,   0x1000
factory,    app,  factory, 0x10000,  0x200000
assets,     data, 0x40,    0x210000, 0x5D0000
game_save,  data, 0x41,    0x7E0000, 0x20000
```

| 区域 | 大小 | 主要内容 |
| --- | ---: | --- |
| 系统前置区 | 64 KB | Bootloader、分区表、NVS、PHY |
| App | 2.00 MB | ESP-IDF、BSP、LVGL、游戏代码与少量核心常量 |
| Assets | 5.81 MB | 背景、精灵、图标、字体、文本、音乐和音效 |
| Game save | 128 KB | A/B 双份存档、CRC、日志、设置和迁移临时区 |

资源区可以使用自定义打包格式或只读文件系统。若使用 LittleFS/SPIFFS，必须在实际容量预算中计入文件系统元数据、块对齐和预留空间。对于发布后只读的打包资源，简单索引加原始分区读取通常更节省空间。

## 6. MVP 内容规模

根据功能设计，第一版 MVP 包含：

- 14 天春季日历、四时段和 4 种天气。
- 4 个建设阶段的驿站主场景。
- 驿站、安排、农田、旅行和背包 5 个一级模块。
- 4 位宠物伙伴，每位至少 4 组视觉表现。
- 4 个岗位、4 种作物、5 个配方、6 个建设项目。
- 1 个短途旅行目的地和 4 张组合旅行画面。
- 6 名重要旅客、6 种普通旅客模板和至少 24 条普通台词。
- 约 65 个事件，每个事件 3～6 页短文本。
- 10 个主线任务和完整第一章。
- 8 个相册插图槽位。
- 1 项 20～30 秒的烹饪火候小游戏。
- 2～4 组主界面音乐、开场/庆典短曲、环境音和短音效。

上述状态机、经济数值、任务、日历、关系和事件逻辑本身的存储与 RAM 成本很低。决定总资源量的是背景、精灵动画、中文字体和音频。

## 7. 推荐的 Flash 资源预算

### 7.1 分类预算

| 内容 | 目标预算 | 可接受上限 | 备注 |
| --- | ---: | ---: | --- |
| App 固件 | 1.20～1.70 MB | 2.00 MB | 包含 ESP-IDF、BSP、LVGL 和游戏逻辑 |
| 场景、开场和相册插图 | 1.30～2.00 MB | 2.20 MB | 索引色、图层复用或分块压缩 |
| 角色、旅客和动画 | 0.50～0.90 MB | 1.00 MB | 小尺寸精灵，表情和动作复用 |
| UI 图标和图集 | 0.10～0.25 MB | 0.30 MB | 使用图集减少索引开销 |
| 中英文字体 | 0.10～0.30 MB | 0.40 MB | 中文必须按文本裁剪字形 |
| 事件文本与数据表 | 0.08～0.20 MB | 0.25 MB | 使用 ID、定长数值和只读表 |
| 音乐和环境音 | 0.70～1.40 MB | 1.60 MB | IMA ADPCM 流式播放或模块音乐 |
| 宠物与 UI 短音效 | 0.10～0.30 MB | 0.35 MB | 低采样率 PCM 或 ADPCM |
| 资源索引、对齐和发布余量 | 0.40～0.80 MB | 不应低于 0.30 MB | 用于系统迭代和内容调整 |

合理优化后，游戏资源预计占用 3.3～5.4 MB。正式制作应以 **4.5 MB 以内**为目标，不要以 5.81 MB 分区上限作为美术和音频的日常制作预算。

### 7.2 不可采用的原始资源方案

如果约 30 张背景、开场和图鉴图片全部以全屏 RGB565 存储：

```text
30 × 153,600 B ≈ 4.39 MiB
```

这还没有计入角色、字体和音频，已经会用掉大部分资源分区。

16 kHz、16 bit、单声道 PCM 的体积为：

```text
16,000 sample/s × 2 B = 32,000 B/s
30 秒 ≈ 960 KB
4 首 30 秒音乐 ≈ 3.84 MB
```

因此，“全屏 RGB565 原图 + 未压缩 PCM 音乐”的方案不能满足完整 MVP。

## 8. 美术资源策略

### 8.1 驿站主场景

不要导出“4 建设阶段 × 4 时段 × 4 天气”的 64 张完整背景。推荐拆分为：

```text
4 个建设阶段的基础场景
+ 4 组时段调色板或局部光照层
+ 晴光、多云阴影、小雨和暴雨叠加层
+ 烟囱、窗灯、旗帜、飞鸟和雨滴等小动画
+ 宠物、旅客和岗位状态精灵
```

主场景整体目标建议控制在 400～800 KB。

### 8.2 其他场景

- 大厅白天/夜晚使用同一基图加调色板或局部灯光层。
- 农田 4/6 地块使用共享地表和可替换地块。
- 厨房修复只替换炉灶、桌面和装饰等局部图层。
- 森林和旅行场景复用天空、地面、树木和前景瓦片。
- 8 张相册插图可以用 160 × 120 或类似尺寸，在屏幕中以画框形式展示。

### 8.3 储存与绘制格式

推荐优先级：

1. 小图、图标、角色：索引色或透明图集。
2. 场景：瓦片、分层索引色或可分块解压的 RGB565。
3. 大图：按行或按小块解压，禁止整屏解码。
4. 变色：优先替换调色板，不保存多份完整图。
5. 静态图压缩：优先 RLE、Heatshrink 或可小块解压的自定义格式。

不建议在首版直接使用需要大型输出缓冲的 PNG/JPEG 通用解码路径。

## 9. 音频资源策略

### 9.1 推荐方案 A：模块音乐/轻量合成

像素风音序器或 tracker 风格与游戏美术风格匹配，每首音乐通常只需数 KB 到数十 KB。4 首主题音乐可能控制在 50～200 KB，但需要实现轻量混音和波形合成。

### 9.2 推荐方案 B：IMA ADPCM 流式播放

4 bit IMA ADPCM 约为 16 bit PCM 体积的四分之一。16 kHz 单声道约为 8 KB/s：

```text
4 首 × 30 秒 × 8 KB/s ≈ 960 KB
```

加上环境音和短音效后，总音频资源可控制在 1.1～1.5 MB。ADPCM 应从 Flash 分块读取，解码成小块 PCM 后立即送入 I2S，不保存整首解码音频。

### 9.3 首版取舍

功能设计已允许将四时段音乐简化为两组：

- 清晨/白天。
- 黄昏/夜晚。

建议先完成两组循环音乐，但保留四时段音乐 ID，后续有资源余量时再替换为四首独立音乐。

## 10. 字体和文本预算

65 个事件、主线、旅行日记和 UI 文本本身占用不大，UTF-8 文本和结构化表预计可控制在 80～200 KB。中文字体才是主要开销。

必须从定稿文本提取实际使用字符，生成子集字库。不应嵌入完整中文字体。

建议：

- 主 UI 使用 14～16 px 点阵或 1 bit/2 bit 字形。
- 标题仅保留少量 20 px 字形。
- 数字、时间和常用 ASCII 作为独立小字体。
- 开发构建在缺字时显示明确替代符，并在资源构建阶段检查所有本地化文本。

当前仓库规范规定 UI 文本保持英文，而游戏设计包含语言设置。如首版发布中文，应在开发前明确调整该工程约定，并将中文字库生成纳入资源构建流程。

## 11. 存档预算

存档需要保存的核心内容为状态和 ID，不是资源本体：

- 4 位宠物的岗位、经验、体力、心情和亲密度。
- 6 对宠物关系。
- 最多 6 块农田、2 个厨房槽和各类长期任务。
- 物品数量、品质和锁定状态。
- 65 个事件的解锁、完成、冷却和选择状态。
- 最多 3 个待处理重要事件。
- 最近 10 条日志和待领取报告。
- 时间基准、随机种子、存档版本、校验和设置。

单份存档预计为 4～12 KB。128 KB 分区可以容纳：

- A/B 双份存档。
- CRC 或更强校验。
- 写入中断恢复标记。
- 存档版本迁移临时空间。
- 少量历史日志和调试摘要。

背景、头像、旅行照片和事件正文必须保存在只读资源区，存档仅保存它们的资源 ID 和解锁状态。

## 12. 推荐的运行时 RAM 预算

### 12.1 目标分配

| 模块 | 目标 RAM | 说明 |
| --- | ---: | --- |
| LVGL 内存池 | 24 KB | 现有配置，调整后必须重测 |
| LCD DMA 条带 | 9.6 KB | 现有单缓冲 |
| I2S TX DMA | 约 5.6 KB + 描述符 | 正式游戏建议只创建 TX |
| 核心游戏状态 | 8～16 KB | 常驻状态、队列和小型表索引 |
| 当前页 LVGL 对象 | 8～20 KB | 离开页面后销毁，不缓存全部页面 |
| 图片解压/转色 | 5～12 KB | 不得整屏解码 |
| 音频解码和流缓冲 | 6～12 KB | 小块 ADPCM 解码或合成器状态 |
| 游戏工作任务栈 | 6～12 KB | 应用栈高水位校准 |
| 存档序列化临时区 | 4～8 KB | 流式写入时可进一步减少 |
| 安全余量 | ≥ 24～32 KB | 用于驱动峰值、碎片和异常路径 |

游戏新增常驻和工作 RAM 建议控制在 50～75 KB。该目标只是设计预算，能否达成需要使用完整游戏固件构建和实机运行日志验证。

### 12.2 页面和状态管理规则

- 仅保留当前页面和必要的全局状态。
- 离开农田、旅行、图鉴或事件页后立即销毁其 LVGL 对象。
- 不同时预加载多个全屏背景。
- 台词和事件数据从 Flash 按 ID 读取，当前页只缓存展示所需的少量文本。
- 离线结算按任务完成时间计算，不为每个长期任务创建常驻 FreeRTOS 任务或计时器。
- 图片、音频和存档缓冲分时复用，避免多个大块同时存在。

## 13. 对当前 BSP 的资源优化建议

1. **正式游戏只创建 I2S TX**  
   当前 BSP 在启动时创建全双工 TX/RX。游戏不需要麦克风时，可回收 RX DMA 及其驱动对象。

2. **取消 96 KB 整段录音缓冲**  
   正式游戏不应包含该峰值分配。如未来需要麦克风互动，必须采用小型环形缓冲和流式处理。

3. **音频按需初始化**  
   若驱动释放/重建成本和可靠性可接受，可在需要播放时创建音频资源，长时间静音时停止或释放。

4. **保持 LCD 20 行单缓冲**  
   在完成音频、图片解码和页面峰值实测前，不应改成大行数双缓冲。

5. **不盲目扩大 LVGL 内存池**  
   页面复杂度优先通过销毁非活动页面、精简样式和复用对象解决。

## 14. 可行性结论

在不考虑 OTA 的前提下，以下 MVP 内容均可在当前硬件上实现：

- 14 天春季日历、四时段、天气和离线结算。
- 4 位宠物、岗位、心情、体力、经验和两两关系。
- 农田、厨房、接待、森林和短途旅行。
- 约 65 个事件、10 个主线任务和 6 名重要旅客。
- 建设阶段、四时段和天气叠加的驿站壁纸。
- 精灵动画、事件表情、8 张相册插图和火候小游戏。
- 中文/英文文本，前提是使用裁剪字库。
- 循环音乐、环境音和短音效，前提是流式压缩或轻量合成。
- A/B 双份本地存档和断电恢复。

完整 MVP 不可接受的实现方式是：

- 大量全屏 RGB565 原图。
- 未压缩长 PCM 音乐。
- 完整中文字库。
- 全屏图片解码缓冲。
- 整段长音频加载到 RAM。
- 同时保留多个页面和多张背景。

## 15. 待构建与实机验证项

### 15.1 构建后数据

完成 ESP-IDF 5.5.x 环境后执行：

```bash
idf.py build
idf.py size
idf.py size-components
idf.py size-files
idf.py partition-table
```

应记录：

- App 二进制镜像大小。
- DRAM `.data` 和 `.bss` 大小。
- IRAM 使用。
- Flash code 和 rodata 大小。
- LVGL、音频、字体和游戏主组件的分项占用。

### 15.2 运行时数据

应在以下节点记录普通堆、DMA 堆、历史最低堆和最大连续块：

1. 系统启动但尚未初始化外设。
2. 显示和 LVGL 初始化后。
3. 按键、电池和音频初始化后。
4. 驿站主场景完全加载后。
5. 进入最复杂的安排/图鉴/事件页后。
6. 背景解压与音乐播放并发时。
7. 存档写入、离线结算和页面切换同时发生时。
8. 连续运行 24 小时后。

建议记录的 API：

```c
heap_caps_get_free_size(MALLOC_CAP_8BIT);
heap_caps_get_largest_free_block(MALLOC_CAP_8BIT);
heap_caps_get_free_size(MALLOC_CAP_DMA);
heap_caps_get_largest_free_block(MALLOC_CAP_DMA);
esp_get_minimum_free_heap_size();
```

### 15.3 通过标准

- 最复杂页面和音频并发时不发生分配失败。
- 运行时最低空闲堆不低于 32 KB。
- 关键运行状态下最大连续 DMA 空闲块不低于 16 KB。
- 页面反复进出后空闲堆和 LVGL 对象数不持续下降。
- 音频播放、背景刷新和按键操作并发时无 I2S/LCD `NO_MEM`。
- 存档写入中断后可恢复最近一份有效存档。
- 发布资源包不超过 4.5 MB 目标，且不超过资源分区实际可用容量。

## 16. 开发阶段的资源门禁

每次新增背景、字体、音频、LVGL 页面或任务时，必须回答：

1. 资源是否常驻 RAM？
2. 最大单次连续分配是多少？
3. 是否必须使用 DMA 能力内存？
4. 是否与 LCD、I2S 或存档操作并发？
5. 是否可以在离开页面时释放？
6. 是否可以改为分块、流式或图层复用？
7. 增加后的 App、Assets、free heap 和 largest block 还剩多少？

未提供构建数据和实机内存数据的大型资源修改，不应直接进入发布版本。
